## Finding 1 — `out.json` has a surviving child, and it is the render acceptance target

`py/render/qa/` — 35 MB, tracked, and **referenced by zero lines of code anywhere in
the repository.** Grep across every `.py`, `.md` and `.json` outside that directory
returns nothing.

Contents: `seidensticker_render.json`, `seidensticker_profile.json`,
`seidensticker_qa_input.json`, two 17 MB `.pptx` files, `reference_slide6.png`,
`seidensticker_slide6.png`, `seidensticker_render_slide6.png`.

`seidensticker_render.json` carries a **nine-year FY2017–FY2025 Umsatzerlöse series.**
Multi-year assembly does not exist in this codebase. The values match `out.json`'s
deleted `reconciliation` block to the cent — FY2021 100,393,437.35, FY2024
103,152,036.57, FY2025 111,815,106.14. Same superseded `p0_normalise` lineage, same
epistemic status, still in the tree.

And `reference_slide6.png` is positioned as the render layer's acceptance reference.
**You deleted the parent and promoted the child to acceptance criterion.**

Wave 0 action: move `py/render/qa/` to `_quarantine/` or delete it. If any of it is
needed as a render fixture, it must be regenerated by current code and carry its
producer's SHA. Also: 35 MB of binary in a source tree that four worktrees will each
check out is 140 MB of avoidable disk and clone time.

### The structural version of this problem

You have now deleted `out.json` twice and it keeps having children. Vigilance is not
the fix, because **the repo has no provenance for its own artifacts** — a JSON emitted
by a code path that no longer exists is indistinguishable on disk from one emitted by
current code. Both are plausible, both spot-check clean, and the fabricated parts are
exactly the parts nobody checks.

Fix, ~20 lines, ends the class permanently:

- Every artifact the pipeline emits carries `_meta: {git_sha, producer_module, produced_at}`
- Every consumer refuses an artifact whose `git_sha` is not an ancestor of `HEAD`
- CI fails on any tracked `.json` under `py/` or `tests/fixtures/` lacking `_meta`

Your design principle — *a confidently wrong output is worse than a crash* — is
currently enforced against the client's numbers and not against the pipeline's own
outputs. That asymmetry is where all three incidents came from.

## Finding 3 — V10 is Lane A's witness, and it is already written

`contract/rules.json`:

```json
"V10": { "severity": "note_required", "check": "a subtotal must equal the sum of its component lines" }
```

Implemented at `py/validate/validator.py:392`, with an expected/actual/delta message.

It currently has nothing to check. The rows it would check — Gesamtleistung, the
Materialaufwand total, the Personalaufwand total, the operating-expense block, the
Finanzergebnis — are exactly the rows `_column_actuals` discards at line 220 before
the mapper sees them.

**So Lane A's acceptance is not a new test. It is: after the guard is removed, V10
fires clean on the FY2024 fixture.** That is a witness written before the fix, by a
different module, against arithmetic the filing states about itself. It is the second
figure in this project to have one. Drop the bespoke assertion I specified in v1.

Corollary worth internalising: the review queue under-reports by exactly the subtotal
rows, and subtotals are where a filing states its own arithmetic. The rows you were
losing were the rows that make the rest checkable.
